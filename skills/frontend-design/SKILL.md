# 前端设计

根据产品本身形成清晰、有辨识度的界面，并交付能运行的实现。

## 先理解内容与约束

- 先确定产品、受众和当前页面帮助用户完成的主要任务。信息不足但不影响实现时，简短说明假设后继续；缺失信息会实质改变设计时再询问。
- 阅读项目规则与现有实现，沿用技术栈、组件库、主题、设计令牌和交互约定。品牌要求、参考图和用户明确指定的风格优先于本技能的审美偏好。
- 在已有项目中，通过主题或已有 CSS 变量使用颜色。需要新增令牌时集中定义，不在组件中散落硬编码颜色。不要为追求新颖而替换现有框架、引入未经授权的依赖或破坏组件行为。
- 生成涉及具体库 API 的代码前，核实项目依赖版本，并按项目要求查阅对应版本文档。

## 先定方向，再实现

实施前简短确定颜色、字体、布局和一个主要视觉特点，计划长度与任务大小相称。

- **颜色**：新项目可建立约 4–6 个有语义名称的基础色；现有项目优先映射已有主题令牌。配色由产品内容和品牌决定。
- **字体**：通常使用一个家族，或两个角色清晰、差异明确的家族。设置字号层级、字重、字距和行高，兼顾中文、数字与回退字体。字体不设通用黑名单；现有产品字体合适时继续使用。正文行长通常控制在约 80 个字符以内，并根据语言和阅读场景调整。
- **布局**：说明主次关系、对齐、阅读顺序与响应式变化；确有比较价值时再画简短线框。让内容结构决定布局。
- **特点**：选择一个来自行业、材料、内容或用户任务的视觉特点，将主要表现力集中在这里。

实现前检查：方案中的每个关键选择是否有本项目的依据？如果换个产品仍能原样套用，应重做缺乏依据的部分。小范围修改只需局部判断，不强制完整设计提案或额外审批。

## 以布局和操作引导易用性

界面首先应让用户看懂当前内容、找到下一步并完成任务。通过布局和控件建立清晰的操作路径，再为确有必要的信息提供文字说明。

- 按用户任务和阅读顺序组织信息，将相关内容与操作放在一起。用分组、对齐、间距和层级表达关系，避免用户阅读说明书才能理解页面结构。
- 明确当前任务的主要操作与次要操作，将按钮放在其作用对象或流程节点附近。危险操作与常用操作适当分隔；同类操作在各页面保持一致的位置和命名。
- 按钮文字说明具体动作，控件应有清晰的状态、可见反馈和足够的点击区域。表单错误靠近相应字段，完成操作后清楚显示结果及可继续的动作。
- 不通过大段功能说明、装饰性标签、仅悬浮可见的 title/tooltip 或图像 alt 来补救难以理解的布局。若必须解释按钮在哪里、先点什么或卡片之间是什么关系，应先检查并改进布局与控件表达。
- 关键操作名称、必要输入条件和影响用户决策的信息，应在需要的位置可见；tooltip 只补充次要细节，不承载完成任务必需的信息。
- 保留正确的无障碍语义：有意义的图片提供恰当 alt，装饰图使用空 alt；图标按钮提供可访问名称，例如 aria-label，名称与实际动作一致。可访问名称不能代替对所有用户都清楚的布局与操作表达；新颖或含义不明确的图标应增加可见动作文字。
- 对复杂规则、不可逆后果、首次使用或法定要求提供与风险相称的说明。不要为减少文字而隐藏必要信息，也不要为了“无说明也能用”而省略无障碍支持。

## 视觉执行

- 首屏呈现对当前任务最有价值的内容：可以是标题、图像、实时数据、交互演示或操作区，不强制使用营销式 hero。
- 边框、分隔线、编号、标签和卡片应表达真实的信息结构。编号用于步骤、时间或业务顺序；不要给无顺序的内容装饰性编号。
- 不机械套用奶油底配衬线标题、深底配荧光强调色、报纸式细线分栏、同形圆角卡片、渐变装饰、全大写眉题或链接尾部箭头。这些手法与需求相符时仍可使用。
- 不默认给标题中的单个词换色、加粗或斜体，不为每块内容添加小标题和装饰标签。
- 自动播放的动效应少而有目的。优先用动效解释用户操作造成的变化，避免每个区块都淡入上移、每张卡片都悬停浮起。尊重减少动态效果设置。
- 管理 CSS 作用域和选择器优先级，避免布局与组件样式相互覆盖。用清晰的间距、对齐、比例和层级建立品质，删去不服务内容的装饰。

## 成品 UI 文案：明确拒绝无意义内容

文案需要帮助用户操作、判断、定位或理解结果。不能说明用途的文字应删除，而不是改成更华丽的表达。

- **拒绝模板占位词**：成品界面不保留“标题”“副标题”“功能介绍”“描述内容”“待补充”“Lorem ipsum”等未完成文本。表单中具有实际引导作用的 placeholder 可以保留。
- **拒绝大段功能自述**：不要默认添加“本系统支持……”“通过本功能您可以……”等重复可见控件含义的介绍。除非用户要求介绍页、帮助或引导，否则优先呈现任务、数据和操作。必要的规则说明、确认后果、错误恢复及空状态指引应保留，长度与任务复杂度相称。
- **拒绝开发过程文案进入产品**：P0/P1/P2 优先级、验收条目、设计意图、实现原理、技术栈、组件说明及开发者给交付物的评语，应放在交付说明中；仅在它们确实属于该产品的业务内容时显示，例如工单的 P1 优先级。不要仅因文字包含 P1 就删除真实业务信息。
- **拒绝装饰性解释与标签**：不要用“核心能力”“高效协同”“智能赋能”等泛化口号填空，也不要给每个字段、按钮和卡片附加无助于决策的解释。标题已有信息不在段落中复述。
- 缺少真实内容时先复用项目已有文案和数据。用户允许演示时，采用具体、可信且明确属于演示的数据；不得把编造的指标、客户、评价或成功状态当成事实。不能合理补全的信息采用诚实的空状态，且不要用空状态逃避已授权的功能实现。
- 使用用户理解的业务词汇与简洁、主动的表达。按钮说明实际动作，同一动作在按钮、确认框和结果反馈中使用一致名称。
- 错误说明发生了什么以及如何继续；空状态提供有用的下一步。不要用含糊失败提示、拟人化道歉或宣传文案替代指引。

## 完成后复核

- 在工具可用时运行页面，检查桌面与窄屏截图，并实际验证主要操作。仅运行构建不能视作完成视觉验收。
- 沿真实用户任务走查布局和按钮：主要操作是否易找、次要与危险操作是否可区分、控件是否靠近作用对象、结果反馈是否清楚？如果移除冗余功能介绍后路径变得难懂，先修正信息结构和操作表达，保留任务必需的说明。
- 检查键盘焦点、可读性、对比度、响应式溢出、减少动态效果及真实可用的交互。
- 单独检查页面中所有可见标签、段落、提示和演示数据：是否残留模板词、无业务意义的 P1 标签、设计说明、重复解释或长篇功能自述？逐项删除或改为完成任务必需的内容。
- 删除一处不必要的装饰或文字，或确认它确有用途。最终说明实现结果、实际完成的验证和仍未验证的部分；开发说明留在交付消息中。
